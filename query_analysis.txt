HEALTHCARE ANALYTICS LAB - PART 2: OLTP QUERY ANALYSIS
================================================================

Measurement method (applies to all four questions):
- Environment: MySQL 8.0 in MySQL Workbench, on a laptop.
- Data: database healthanalyticsdb loaded with the brief's sample data
  plus the deterministic synthetic data from
  sql/oltp/03_synthetic_data.sql: 200,004 encounters, 20,003 patients,
  100 providers, 464,820 encounter_diagnoses rows, 281,773
  encounter_procedures rows and 189,882 billing rows. (On the 4-row
  sample data alone, every query finished in under 0.2 ms, which is
  too small to show any bottleneck.)
- Execution time: total "actual time" from the top line of a single
  EXPLAIN ANALYZE run. Full plans: results/oltp_explain_analyze/
  oltp_q1.txt to oltp_q4.txt.
- Rows scanned: rows x loops, summed over the table-access lines of
  the plan (table scans and index lookups). "Estimated" uses the
  optimizer's cost estimates (cost=... rows=...); "actual" uses what
  EXPLAIN ANALYZE measured. Joins, sorts and aggregates process rows
  that were already read, so they are not added again.
- Runtime percentages: estimated by comparing the finish times of
  consecutive plan steps. They are approximate, because pipelined
  steps can overlap.

QUESTION 1: Monthly Encounters by Specialty

SQL Query:
SELECT
    CAST(DATE_FORMAT(en.encounter_date, '%Y-%m-01') AS DATE) AS encounter_month,
    sp.specialty_name,
    en.encounter_type,
    COUNT(*)                      AS total_encounters,
    COUNT(DISTINCT en.patient_id) AS unique_patients
FROM encounters en
LEFT JOIN providers   pr ON pr.provider_id  = en.provider_id
LEFT JOIN specialties sp ON sp.specialty_id = pr.specialty_id
GROUP BY encounter_month, sp.specialty_name, en.encounter_type;

Schema Analysis:
- Tables joined: encounters, providers, specialties
- Number of joins: 2 (both LEFT JOIN)

Performance:
- Execution time: 2.910 seconds (2,910 ms)
- Estimated rows scanned: 598,449 (actual: 600,012)
  (encounters: 200,004 via full table scan;
   providers: 200,004 via primary-key lookups, one per encounter;
   specialties: 200,004 via primary-key lookups, one per encounter)

Bottleneck Identified:
1. JOIN chain (about 50% of runtime). The specialty name is not stored
   on the encounter, so every encounter row needs two extra
   primary-key lookups (encounters -> providers -> specialties), shown
   as loops=200004 on both lookup lines. That is 400,008 lookups
   before any counting can start: the full scan finished at 282 ms,
   the provider lookups at 965 ms and the specialty lookups at
   1,452 ms.

2. Month calculation on every row (about 18% of runtime). The "Stream
   results" step (1,452 -> 1,987 ms) prepares each of the 200,004
   joined rows for sorting, which includes computing the month with
   DATE_FORMAT on every encounter_date.

3. Sort for GROUP BY (about 23% of runtime, 1,987 -> 2,650 ms). MySQL
   groups rows by sorting all 200,004 of them on (month, specialty,
   encounter type). The month is computed at query time and
   specialty_name comes from another table, so no existing index
   (including idx_encounter_date) can deliver rows already in group
   order. The plan shows the Sort step even without ORDER BY, which
   confirms it is caused by the GROUP BY.

4. Aggregation (about 9% of runtime). COUNT(DISTINCT patient_id) must
   track which patients it has already seen in each group, which is
   more expensive than a plain COUNT(*).

Root cause: the data needed for the report is spread across three
normalized tables, and the month must be derived at query time. Every
run repeats the same 400,008 lookups, 200,004 date calculations and a
200,004-row sort over the full encounters table.

QUESTION 2: Top Diagnosis-Procedure Pairs

SQL Query:
SELECT
    d.icd10_code,
    p.cpt_code,
    COUNT(DISTINCT ed.encounter_id) AS encounter_count
FROM encounter_diagnoses ed
JOIN encounter_procedures ep ON ep.encounter_id = ed.encounter_id
JOIN diagnoses  d ON d.diagnosis_id = ed.diagnosis_id
JOIN procedures p ON p.procedure_id = ep.procedure_id
GROUP BY d.icd10_code, p.cpt_code
ORDER BY encounter_count DESC, d.icd10_code, p.cpt_code;

Schema Analysis:
- Tables joined: encounter_diagnoses, encounter_procedures, diagnoses,
  procedures
- Number of joins: 3 (all INNER JOIN)
- How the junction tables are joined: diagnoses and procedures have no
  direct relationship. The two junction tables are joined to each other
  on their shared encounter_id, which pairs every diagnosis of an
  encounter with every procedure of the same encounter. diagnoses and
  procedures are then joined to translate IDs into ICD-10 and CPT codes.

Performance:
- Execution time: 12.757 seconds (12,757 ms)
- Estimated rows scanned: ~1,496,600 (actual: 1,799,001)
  (procedures: 100 via full table scan;
   encounter_procedures: 281,773 via index lookups on procedure_id,
      100 lookups of ~2,818 rows each;
   encounter_diagnoses: 758,564 via index lookups on encounter_id,
      one lookup per encounter_procedures row, ~2.69 rows each;
   diagnoses: 758,564 via primary-key lookups, one per pair row)
- Note: at this data volume MySQL chose a different plan than on the
  sample data. It now starts from the procedures table and reaches
  encounter_procedures through the automatic index on procedure_id.

Bottleneck Identified:
1. Row explosion from joining two junction tables (about 46% of
   runtime on its own). Each encounter produces (number of diagnoses x
   number of procedures) rows. In the plan, 281,773 procedure rows
   become 758,564 pair rows when joined to encounter_diagnoses
   (1,365 -> 7,294 ms). An inpatient stay with 10 diagnoses and 15
   procedures alone would produce 150 rows before any counting.

2. Code lookups on the exploded rows (about 18% of runtime). Every one
   of the 758,564 pair rows needs a primary-key lookup in diagnoses to
   get its ICD-10 code (7,294 -> 9,644 ms). The explosion multiplies
   this lookup work too. Together with the explosion, the scans and
   joins take about 81% of the runtime.

3. Sort for GROUP BY (about 13% of runtime). MySQL sorts all 758,564
   exploded rows by (icd10_code, cpt_code) to group them
   (10,366 -> 12,080 ms).

4. COUNT(DISTINCT encounter_id) must deduplicate encounters within
   each group (about 5%). The final ORDER BY sorts only the 7,493
   result rows, which takes about 20 ms (0.2%).

Root cause: the schema never stores diagnosis-procedure pairs. They
exist only implicitly through a shared encounter_id, so every run must
rebuild all pairs from scratch, and the intermediate row count grows
with diagnoses x procedures per encounter rather than with the number
of encounters. Here 200,004 encounters produce 758,564 pair rows.

QUESTION 3: 30-Day Readmission Rate

SQL Query:
SELECT
    sp.specialty_name,
    COUNT(DISTINCT idx.encounter_id) AS inpatient_discharges,
    COUNT(DISTINCT CASE WHEN re.encounter_id IS NOT NULL
                        THEN idx.encounter_id END) AS readmissions,
    ROUND(100 * COUNT(DISTINCT CASE WHEN re.encounter_id IS NOT NULL
                                    THEN idx.encounter_id END)
              / COUNT(DISTINCT idx.encounter_id), 2) AS readmission_rate_pct
FROM encounters idx                                    -- the inpatient stay
LEFT JOIN encounters re                                -- a possible return visit
       ON re.patient_id = idx.patient_id
      AND re.encounter_date >  idx.discharge_date
      AND re.encounter_date <= DATE_ADD(idx.discharge_date, INTERVAL 30 DAY)
LEFT JOIN providers   pr ON pr.provider_id  = idx.provider_id
LEFT JOIN specialties sp ON sp.specialty_id = pr.specialty_id
WHERE idx.encounter_type = 'Inpatient'
GROUP BY sp.specialty_name
ORDER BY readmission_rate_pct DESC;

Schema Analysis:
- Tables joined: encounters (as idx, the inpatient stay),
  encounters (as re, the return visit; self-join), providers,
  specialties
- Number of joins: 3 (all LEFT JOIN)
- How a readmission is detected: each inpatient encounter (idx) is
  joined to the same table (re) to find another encounter for the
  same patient that starts after idx.discharge_date and no more than
  30 days later. If such an encounter exists, the inpatient stay
  counts as readmitted. The self-join is a LEFT JOIN so that stays
  without a return visit stay in the denominator, and
  COUNT(DISTINCT idx.encounter_id) ensures a stay with several return
  visits counts only once. Assumptions: a return of any encounter type
  counts, and the readmission is attributed to the specialty of the
  original inpatient stay.

Performance:
- Execution time: 2.672 seconds (2,672 ms)
- Estimated rows scanned: ~827,200 (actual: 626,446)
  (encounters as idx: 200,004 via full table scan, filtered to 32,436
      inpatient stays;
   encounters as re: 356,796 via index lookups on patient_id, one per
      inpatient stay, ~11 rows each, then filtered by date to 13,072;
   providers: 34,823 and specialties: 34,823 via primary-key lookups)

Bottleneck Identified:
1. Self-join on encounters (about 72% of runtime on its own,
   313 -> 2,233 ms). For each of the 32,436 inpatient stays, the
   patient_id index returns every encounter that patient has ever had
   (about 11 each, 356,796 rows in total), and the 30-day date
   condition is then checked row by row: on average only 0.4 of the
   11 rows per stay passes. The cost grows with inpatient stays x
   encounters per patient, so frequent visitors are the most
   expensive. Without the patient_id index, every inpatient stay would
   be compared against the entire encounters table.

2. Full table scan to find inpatient stays (about 12% of runtime).
   There is no index on encounter_type, so all 200,004 encounters are
   read and filtered to keep the 32,436 inpatient ones.

3. JOIN chain to the specialty (about 9% of runtime). The joined rows
   need 34,823 provider and 34,823 specialty lookups.

4. Grouping and aggregation (about 5% combined). The joined rows are
   sorted by specialty and four COUNT(DISTINCT) expressions are
   computed. The rate formula repeats both counts, so MySQL computes
   each one twice.

Root cause: a readmission is a relationship between two encounters of
the same patient across time, but the normalized schema stores each
encounter independently and records no readmission flag. Every run
must rediscover readmissions from scratch by matching each inpatient
stay against the patient's full encounter history.

QUESTION 4: Revenue by Specialty & Month

SQL Query:
SELECT
    CAST(DATE_FORMAT(en.encounter_date, '%Y-%m-01') AS DATE) AS encounter_month,
    sp.specialty_name,
    SUM(b.allowed_amount) AS total_allowed
FROM billing b
JOIN      encounters  en ON en.encounter_id = b.encounter_id
LEFT JOIN providers   pr ON pr.provider_id  = en.provider_id
LEFT JOIN specialties sp ON sp.specialty_id = pr.specialty_id
GROUP BY encounter_month, sp.specialty_name
ORDER BY encounter_month, total_allowed DESC;

Schema Analysis:
- Tables joined: billing, encounters, providers, specialties
- Number of joins: 3 (billing -> encounters is an INNER JOIN, since
  every claim belongs to an encounter; providers and specialties are
  LEFT JOINs, so revenue with a missing specialty is still counted,
  under a NULL specialty)
- JOIN chain: billing -> encounters -> providers -> specialties. The
  amount is stored in billing, the service date in encounters, and the
  specialty name two tables further away, so all four tables are
  needed to build each output row.
- Assumptions: "month" is the month of service (encounter_date), and
  all claims are included regardless of claim_status.

Performance:
- Execution time: 2.798 seconds (2,798 ms)
- Estimated rows scanned: 758,332 (actual: 759,528)
  (billing: 189,882 via full table scan;
   encounters: 189,882 via primary-key lookups, one per billing row;
   providers: 189,882 via primary-key lookups, one per billing row;
   specialties: 189,882 via primary-key lookups, one per billing row)

Bottleneck Identified:
1. JOIN chain (about 68% of runtime). The specialty is three tables
   away from the amount being summed, so every billing row needs three
   primary-key lookups (loops=189882 on each lookup line): 569,646
   lookups before any summing can start. The scan finished at 233 ms,
   the encounter lookups at 972 ms, the provider lookups at 1,470 ms
   and the specialty lookups at 1,898 ms.

2. Aggregation in a temporary table (about 32% of runtime,
   1,898 -> 2,798 ms). The grouping keys come from two different
   tables (month from encounters, specialty_name from specialties),
   and the month is computed with DATE_FORMAT on every row. No index
   can supply rows in group order, so MySQL builds an internal
   temporary table to accumulate the sums ("Aggregate using temporary
   table" in the plan); every one of the 189,882 rows is inserted into
   or updated in it.

3. Final sort (negligible). ORDER BY total_allowed DESC sorts by a sum
   that only exists after aggregation, so a separate sort is needed,
   but it only handles one row per month and specialty (240 rows) and
   takes well under 1 ms. This confirms that the final sort does not
   grow with the data; the joins and the aggregation do.

Root cause: the three pieces of information the report needs (amount,
service date, specialty) live in three different normalized tables,
linked only through foreign keys. Every run must rebuild the
billing -> encounters -> providers -> specialties chain for every
claim, derive the month at query time, and aggregate the result in a
temporary table.
